# P2-auth: Implement SISNA (Starknet Sign-In With Agent) Nonce/Verify/Receipt Package

## Summary

Implement a Starknet-native sign-in flow: generate nonces, verify signatures, and issue receipts — analogous to SIWE but designed for agent-to-agent and agent-to-user authentication on Starknet.

## Context

The no-backend launch is self-custodial and does not require interactive authentication. However, managed-backend deployments need a standardised sign-in mechanism so that users can prove identity via Starknet signatures without exposing private keys. SISNA fills this gap.

## Requirements

- [ ] **Nonce generation**: Cryptographically secure random nonce, stored with TTL
- [ ] **Signature verification**: Verify Starknet ECDSA signature against signer address
- [ ] **Receipt issuance**: On successful verify, issue a signed receipt token
- [ ] **Nonce TTL**: Nonces expire after configurable window (default: 5 minutes)
- [ ] **Replay protection**: Each nonce can only be used once
- [ ] **Standard message format**:
  ```
  Sign in with Starknet Agent
  Domain: {domain}
  Statement: {statement}
  URI: {uri}
  Version: 1
  Chain ID: {chain_id}
  Nonce: {nonce}
  Issued At: {issued_at}
  ```

## API Contract

```yaml
# Generate nonce
POST /sisna/nonce
Response: {
  "nonce": "0xABC...",
  "expires_at": "2026-01-15T10:35:00Z",
  "domain": "agent.example.com"
}

# Verify signature and get receipt
POST /sisna/verify
Body: {
  "address": "0x...",
  "signature": { "r": "0x...", "s": "0x...", "v": 0 },
  "message": "Sign in with Starknet Agent...",
  "nonce": "0xABC..."
}
Response: {
  "verified": true,
  "receipt": {
    "token": "eyJ...",
    "issued_at": "2026-01-15T10:30:00Z",
    "expires_at": "2026-01-15T11:30:00Z",
    "address": "0x..."
  }
}

# Validate receipt
POST /sisna/validate
Body: { "token": "eyJ..." }
Response: { "valid": true, "address": "0x...", "expires_at": "..." }
```

## Runbook

1. Configure domain/statement: update SISNA config with operator domain and optional statement
2. Rotate verification keys: update Starknet contract address if using on-chain registry
3. Handle receipt expiry: receipts are short-lived; clients must re-authenticate on expiry
