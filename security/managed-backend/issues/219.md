# P0-proxy: HMAC + mTLS + nonce replay protection (Redis TTL)

## Summary

 Harden the inbound proxy with mutual TLS, request HMAC signing, and nonce-based replay protection backed by Redis with TTL eviction.

## Context

The no-backend launch (see #273) defers this work. For the managed-backend profile, the proxy is the trust boundary between untrusted clients and the core engine. Without these guards, the service is vulnerable to replay attacks, MITM, and credential forgery.

## Requirements

- [ ] **mTLS**: All client connections must present a valid certificate signed by the operator CA
- [ ] **HMAC Signing**: Every request signed with HMAC-SHA256 using a per-client shared secret
- [ ] **Nonce Replay Protection**: Each request includes a monotonic nonce; replayed nonces rejected via Redis SET NX with TTL
- [ ] **Redis TTL**: Nonce entries expire after configurable TTL (default: 300s)
- [ ] **Key Rotation**: Support rolling HMAC keys without invalidating in-flight requests
- [ ] **Graceful Degradation**: When Redis is unavailable, proxy must either fail closed or fall back to a safe mode (configurable)

## API Contract

```yaml
# Request headers
X-Client-Id: string          # mTLS CN / operator-assigned ID
X-Nonce: string              # monotonically increasing nonce
X-Hmac-Signature: string     # HMAC-SHA256(base64(request_body), shared_secret)
X-Timestamp: int64           # unix epoch ms (window: ±30s)

# Response on replay
409 Conflict: { "error": "nonce_replayed", "nonce": "..." }
401 Unauthorized: { "error": "hmac_invalid" }
403 Forbidden: { "error": "mtls_failed" }
```

## Testing

- Unit tests for nonce uniqueness check
- Integration test: replay attack simulation
- Integration test: mTLS cert rejection
- Integration test: HMAC signature verification
- Chaos test: Redis unavailability → fail-closed behavior

## Runbook

1. Rotate HMAC key: update operator secret store, set `HMAC_ROTATION_WINDOW`, proxy validates both old and new keys during transition
2. Restart mTLS CA: propagate new CA cert to all proxies and clients
3. Redis outage recovery: monitor `proxy.redis.unavailable` metric, auto-recover on Redis restore
